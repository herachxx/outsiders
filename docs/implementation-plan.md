# Grand Mobile Support Copilot — план реализации

Дата анализа: 30 октября 2026. Основание: условия кейса и локальный handout. Это план, а не реализованный сервис.

## 1. Что требуется

Сервис принимает жалобу из лаунчера или короткий внутриигровой репорт и возвращает язык, категорию, приоритет, признак дубля/спама, извлечённые **утверждения** игрока, черновик ответа с проверенными ссылками на правила, необходимость участия человека, уверенность и объяснение маршрутизации. Пакетный `make predict IN=tickets.jsonl OUT=pred.jsonl` использует тот же pipeline. Отдельный отчёт показывает качество на валидации, стоимость и p95 задержки. Автоответ допустим только для безопасных типовых вопросов после проверки; наказание, платёж, доступ к аккаунту, апелляция и жалоба на администратора остаются у человека.

Ограничения: нет кода игры, API, скриншотов и содержимого базы знаний кроме выданных правил; скриншотов известно только число. Данные нельзя публиковать, деанонимизировать и использовать вне кейса; удалить в установленный срок. PDF называет `tickets_hidden.jsonl` закрытым тестом. Из документов не следует, что доступен реальный сервер поддержки. HTTP API надо демонстрировать локально.

## 2. Наблюдения по данным и последствия

Проверено чтением всех строк: train — 118 337 записей, из них 67 755 complaint и 50 582 report; valid — 1 000, из них 817 complaint и 183 report. В обеих выборках отсутствуют `category` и `priority`. Метки `verdict`, `punishment`, `violation` присутствуют только у жалоб и извлечены из исторического ответа. `other` — 24 046 из 67 755 жалоб train. Медиана длины входного текста без ответа администратора — 20 символов; p95 — 174. Доля `uz` по эвристическому `lang` резко меняется: 642/118 337 в train против 119/1 000 в valid. Это проверка устойчивости, а не повод искусственно подгонять под valid. Между train и valid пересекаются 775 `reporter_hash` (при 839 уникальных заявителях в valid), поэтому valid не является независимым срезом по заявителям. `ticket_id` между файлами не пересекаются.

Исторический ответ администратора и извлечённый из него вердикт **не входят в признаки на инференсе**: иначе получится утечка ответа. `rule_refs_raw` — слова заявителя, которые надо проверять по тексту правил. `images_count > 0` означает лишь наличие вложений, не содержание и не доказанность нарушения. Синтетические никнеймы и hash идентификаторы не публикуются и не попадают во внешние логи.

`taxonomy.json` помечен как черновик. До фиксации версии нужно подтвердить категории, приоритеты и спорный случай `report.help`: пример «телепорт» соседствует с запретом просить телепорт в пункте 3.1 правил. При отсутствии подтверждения маршрутизировать такой случай человеку, не обещая помощь.

**Критичная особенность правил:** в 11 разделах `rules.json` содержится 266 пунктов, но только 101 уникальный текстовый `ref`; например, `2.1` встречается в нескольких разделах с разным смыслом. Идентификатор источника внутри системы — `(rules[].id, points[].ref, version/hash)`, а не один `ref`. Если из сообщения известен только «2.1» и раздел не установлен надёжно, нельзя цитировать произвольно найденный пункт. Проверка существования номера без проверки раздела недостаточна.

## 3. Рекомендуемый стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык и API | Python 3.12, FastAPI, Pydantic v2 | Один язык для обработки данных, моделей и HTTP контракта; строгая схема и автодокументация |
| Табличная классификация | scikit-learn: word/char TF-IDF + LinearSVC или LogisticRegression, калибровка | Сильный, быстрый и объяснимый baseline для коротких сообщений, опечаток и `cp1251`-замен |
| Правила и RAG | Версионированный JSON с ключом `(rules[].id, points[].ref)`; точное сопоставление пункта и раздела плюс лёгкий лексический поиск | Корпус мал; векторная БД сейчас лишняя. Цитата проверяется программно по исходному пункту и разделу |
| Черновик | Сначала шаблоны для безопасных маршрутов; опционально LLM-адаптер со строгим JSON, ограниченным контекстом и отключаемым внешним провайдером | Позволяет сравнить качество и цену; без договора о передаче данных внешнюю LLM на реальные обращения не включать |
| Хранилище демо | SQLite для служебного состояния и правок, файлы моделей локально | Достаточно для демонстрации; без хранения исходных обращений в БД по умолчанию |
| Интерфейс | Простая адаптивная страница администратора, серверные шаблоны + минимальный JS | Очередь, черновик, цитаты и правки без отдельного фронтенд проекта |
| Проверки | pytest, sklearn metrics, скрипт benchmark | Одни и те же функции для API и CLI, проверяемые регрессии |

Опциональная альтернатива после MVP: PostgreSQL и pgvector, если появится большая база знаний и измеренный провал лексического поиска. Не вводить векторный поиск ради текущего небольшого `rules.json`.

## 4. Архитектура и поток одного обращения

`JSON → validation → отделение сообщений игрока от ответов → нормализация копии текста → язык → фильтр критических сигналов → категория и приоритет → поиск дубля → извлечение утверждений → подбор раздела и пункта правила → черновик → проверка цитат и обещаний → решение об эскалации → response`.

Оригинал входа сохраняется только в памяти на время запроса. Нормализация исправляет типичные похожие латинские/кириллические буквы для поиска, но не переписывает цитаты игрока. Поле `lang` из handout используется как подсказка, а определение языка строится по текущему тексту; при коротком/смешанном сообщении — `und` и человек. Для казахского и узбекского шаблоны проверяют носители языка. Русские правила не «переводятся» моделью как официальный текст; `cited` содержит `section_id`, `ref`, хеш версии правил и короткую выдержку из **этого** пункта. Текст игрока — недоверенный ввод: инструкции внутри него не могут менять системные правила, перечень источников или формат ответа.

Факты имеют статус `claimed`, `observed_metadata` или `verified`. Например, «игрок применил чит» — утверждение, `images_count=2` — метаданные, «нарушение доказано» недоступно без просмотра скриншотов. Черновик не должен говорить «по скриншотам видно» и назначать санкцию. Если нет достаточной опоры, выдать нейтральный запрос уточнения или `needs_human=true` без фиктивной цитаты.

Автоматически закрывать можно только узкую группу проверенных информационных вопросов; для хакнутого аккаунта, платежа, апелляции, жалобы на администратора, риска вне игры, читы/мошенничество, спорных доказательств и низкой уверенности — только проект ответа и очередь человеку. `confidence` — калиброванная оценка конкретного классификатора, а не вероятность правильности всего ответа. Сырые пороги подбираются по размеченной валидации и фиксируются в конфиге.

### Решения на границах сценариев

| Вход/состояние | Поведение |
|---|---|
| Жалоба с `images_count>0` | Отметить вложение, не утверждать, что оно доказывает нарушение; черновик только с условной формулировкой, решение человеку. |
| Короткий репорт «помогите», «ау» | `report.offtopic` или неопределённая категория по подтверждённой taxonomy; предложить уточнить проблему, не придумывать её. |
| Платёж, взлом, потеря доступа, жалоба на админа | Приоритет по утверждённым правилам маршрутизации, `needs_human=true`; не обещать возмещение, восстановление или наказание. |
| Жалоба на своё наказание, спорный вердикт | Передать человеку; исторический `verdict` — только метка исхода для анализа, не основание ответа. |
| Указан пункт `2.1` без раздела | Найти возможные разделы; если смысл не позволяет выбрать один, не цитировать пункт и отправить на проверку. |
| Дубль без истории или без `reporter_hash` | Не объявлять дублем; добавить понятную причину `history_unavailable`/`identity_unavailable`. |
| Сообщение на смешанном/неопределённом языке | Не переводить официальное правило как подлинный текст; выбрать язык ответа только при достаточной уверенности, иначе человек. |
| Недоступна модель, источник правил или внешняя LLM | Не выдавать уверенный черновик; структурированный fallback, `needs_human=true`, диагностика без текста тикета в логах. |
| Инструкция внутри обращения «игнорируй правила» | Считать частью обращения, не выполнять; использовать только системный контракт и версионированный источник. |

Порядок принятия решения строгий: обязательная эскалация имеет приоритет над confidence и любой модельной рекомендацией; валидация цитат — обязательный gate перед выдачей черновика; обнаружение дубля не закрывает критическое обращение. Причины эскалации задаются стабильными кодами, а не только свободным текстом.

## 5. Контракт и структура проекта

`POST /triage`: вход `{kind, messages:[{role,ts?,text}], region?, server_lang?, rule_refs_raw?, images_count?, reporter_hash?, reported_hash?, reported_nick?}`. Ответ `{lang, category, priority, is_spam_or_duplicate, extracted:{nickname?,rule_refs,has_evidence,claims:[]}, draft_reply:{lang,text,cited:[{section_id,ref,rules_hash,excerpt}]}|null, needs_human, confidence, reasons:[]}`. Поля примера в PDF сохраняются; расширенная структура `cited` нужна для однозначного внутреннего контроля и может сериализоваться в формат организатора при необходимости. `has_evidence` означает **заявленное/прикреплённое доказательство**, не его подтверждение. `is_spam_or_duplicate` можно дополнить `duplicate_of` только при доступном предыдущем тикете; без истории не угадывать дубль. Неверный JSON или недопустимые поля — 422; внутренняя ошибка модели — контролируемая 503 без данных тикета в ответе. В пакетном режиме ошибка одной строки фиксируется отдельно и не сдвигает соответствие входных и выходных строк.

Предлагаемая структура: `app/api.py` (HTTP), `app/schemas.py` (контракт), `app/normalize.py`, `app/triage.py` (оркестрация), `app/classifier.py`, `app/dedupe.py`, `app/rules.py`, `app/draft.py`, `app/safety.py`, `app/ui/` (очередь), `scripts/prepare.py`, `scripts/train.py`, `scripts/evaluate.py`, `scripts/predict.py`, `tests/`, `configs/`, `Makefile`, `README.md`, `AGENTS.md`, `PROJECT_MAP.md`. Сырые данные — вне Git, путь через переменную окружения; `.gitignore` исключает файлы и производные выборки.

## 6. Пошаговая реализация

Каждый этап заканчивается работающим результатом и проверкой. Коммиты — после локального теста и просмотра diff. Оценка длительности дана для одного разработчика и уточняется после первого прототипа.

1. **Зафиксировать контракт и правила разметки (0,5 дня).** Переписать условия кейса в проверяемые acceptance criteria; обозначить все неоднозначности taxonomy; согласовать с владельцем кейса трактовку приоритетов, автоответа и `report.help`. Результат: версия схемы и перечень ручных решений.
2. **Подготовить безопасный проект и импортер (0,5 дня).** Создать структуру, `AGENTS.md`, `PROJECT_MAP.md`, `.gitignore`; потоково читать gzip/JSONL и проверять схему. Проверка: 118 337 + 1 000 валидных строк, никакие обращения не попали в Git и логи.
3. **Построить честный срез данных и ручную разметку (1–2 дня).** Входной текст формировать только из сообщений до ответа администратора; `reported_player` учитывать как отдельное, потенциально противоречащее свидетельство, но не как подтверждение слов заявителя. Размечать стратифицированные примеры по `kind`, языку, категориям, редким p0/p1 и неоднозначным обращениям. Минимум ~600–1000 примеров с двойной разметкой части и разбором разногласий. Выделить финальный ручной holdout по `reporter_hash`, который не используется для настройки порогов. Фиксировать метки `unknown` и спорные случаи, а не принудительно назначать класс. Проверка: протокол разметки, согласованность аннотаторов, отсутствие пересечения заявителей между собственными train и holdout. Предоставленный `valid` использовать для формата, языковых срезов и доступных меток исхода, но не заявлять на нём accuracy категории или macro-F1 приоритета без независимой ручной разметки.
4. **Базовый API и предсказуемые правила безопасности (0,5–1 день).** Pydantic-схемы, endpoint, `make predict`, правила обязательной эскалации. Проверка: API и пакетный режим возвращают одинаковый JSON; ошибки 422/503 обработаны; платежи/доступ/админ всегда `needs_human=true`.
5. **Классификация, язык и приоритет (1–2 дня).** Начать с char 2–5 и word 1–2 TF-IDF + линейный классификатор на ручных метках; отдельные модели/правила для `kind` и приоритета; оценить более сильную многоязычную модель только если baseline не достиг качества. Приоритет p0/p1 дублировать высокочувствительными правилами и не понижать при неуверенности. Проверка: accuracy категории, macro-F1 приоритета, recall p0/p1 и срезы ru/kk/uz/lat/und, калибровка confidence.
6. **Дедупликация и спам (0,5–1 день).** Правило кейса: тот же `reporter_hash`, близкая проблема, интервал 5 часов; поиск по нормализованным токенам с порогом, настроенным на ручных парах. Для batch обрабатывать записи по `created_at`, но возвращать строки в исходном порядке; для HTTP использовать локальный индекс обращений с TTL. Разделять `duplicate` и `spam` во внутреннем результате, даже если внешний контракт объединяет их. При отсутствии истории — `false` с reason `history_unavailable`. Проверка: одинаковый текст разных игроков не склеивается; старые обращения не склеиваются; повторный прогон batch детерминирован; ложные дубли измерены.
7. **RAG по правилам и извлечение фактов (1 день).** Индексировать уникальный составной ключ `(rules[].id, points[].ref)` и хеш версии; выбирать раздел до пункта, учитывать категорию и контекст, проверять `rule_refs_raw`, отделять утверждение от доказательства. Проверка: каждая цитата существует в текущей версии `rules.json`; тесты на несколько разных `2.1` и `1.1`; неоднозначный номер без раздела не попадает в ответ; ссылка на существующий, но нерелевантный пункт отклоняется ручным аудитом. Не использовать синтетические никнеймы как основание для вердикта.
8. **Безопасные черновики и языки (1–2 дня).** Шаблоны ru/kk/uz для безопасных сценариев; при желании LLM-адаптер в закрытом режиме и только после проверки условий передачи данных. Валидатор запрещает обещания разбана, возврата денег, наказания, фразы о просмотренных скриншотах и неверные/нерелевантные цитаты. Для пустого, сверхкороткого, смешанного и неизвестного языка — нейтральное уточнение или человек; при ошибке LLM — безопасный шаблон/эскалация. Проверить инъекции в сообщении игрока и попытки заставить модель сменить источник правил. Проверка: экспертная слепая оценка 100 черновиков по 1–5, отдельные носители kk/uz, цель — выше baseline шаблонов.
9. **Очередь администратора и обратная связь (1 день, бонус).** Показать вход, категорию/приоритет, `claimed`/metadata, черновик и источники; кнопки «отправить», «править», «эскалировать». Отправка в демо только записывает локальное действие; реальные интеграции после отдельного согласования. Правки сохранять без исходных данных или с коротким сроком хранения. Проверка: сценарии пустого, спорного и критического тикета; нельзя отправить черновик с незаверенной цитатой.
10. **Итоговая оценка и сдача (0,5–1 день).** Прогнать untouched holdout, valid и нагрузку; сравнить baseline/кандидата; посчитать стоимость по реально измеренным токенам и опубликованной цене выбранного провайдера, а локальную модель — по амортизированной стоимости железа. Измерять p95 от приёма запроса до готового JSON, вместе с языком, поиском, генерацией, проверками, сетью и retry. Указать объём и состав тестовых обращений, оборудование, конкурентность, долю ошибок, цену входных/выходных токенов. Отдельно сообщить, какая часть валидной выборки получила ручную разметку. Зафиксировать p50/p95, ограничения и воспроизводимые команды. Проверка: `make test`, `make predict`, `make serve`, `make benchmark`, ручная проверка JSONL и отчёта.

### Минимальные пороги для решения о готовности

Точные критерии оценки, подтверждённые пользователем:

| Критерий | Вес | Как измерять и что проверять локально |
|---|---:|---|
| Классификация | 25% | Accuracy категории и macro-F1 приоритета на скрытом тесте. До сдачи — те же метрики на отдельном вручную размеченном holdout, со срезами по `kind` и языку. |
| Качество черновиков | 30% | Администраторы Grand Mobile слепо оценивают 100 черновиков по шкале 1–5 рядом с реальным ответом. До сдачи — такая же слепая процедура на доступной выборке; записывать оценки по тикетам и критерии рубрики. |
| Отсутствие галлюцинаций | 20% | Каждая цитата правила существует и релевантна; выдуманный пункт обнуляет тикет. До сдачи — программная проверка существования `ref` и ручная оценка релевантности всех цитат в 100 черновиках. |
| Казахский и узбекский | 15% | Качество черновиков на `kk` и `uz` оценивают носители. До сдачи — отдельная выборка на каждом языке, оценка смысла, естественности и точности цитат. |
| Стоимость и латентность | 10% | Не дороже $0,002 за обращение **или** локальная модель; p95 не больше 5 секунд. До сдачи — замер на целевом оборудовании с полным pipeline, включая сеть и повторные попытки. |

Скрытый тест недоступен, поэтому его результат нельзя объявлять проверенным заранее. Дополнительные внутренние защитные пороги: 0 выдуманных ссылок в локальном тесте и 100% обязательной эскалации для помеченных критических случаев. Целевые accuracy и macro-F1 фиксируются после первого baseline и аудита качества ручной разметки; документ не выдаёт желаемое число за достигнутую метрику.

## 7. Главные риски и решения

| Риск | Что делать |
|---|---|
| Обучение на ответе администратора вместо обращения | Запретить `admin`, `verdict`, `punishment`, `violation` во входных признаках; тест на утечку |
| Ложные «доказательства» при `images_count>0` | Только `has_evidence=true` как метаданные; исход проверки вложения неизвестен |
| Неутверждённая taxonomy и конфликт правил | Версионировать, помечать спорные категории, отправлять человеку |
| Редкие kk/uz и кодовое смешение | Ручной набор, языковые срезы, шаблоны с проверкой носителей, fallback `und` |
| Ложные дубли | Проверять того же заявителя + смысл + 5 часов; измерять precision и показывать основания |
| Приватность и лицензия | Данные и производные не в Git/отчёте; LLM API только после разрешения на передачу; настроить удаление |
| Неизвестная актуальность правил | Хеш/версия `rules.json`, повторная проверка цитат при каждой смене версии |

## 8. Что даёт поиск похожих решений

Zendesk Intelligent Triage классифицирует тему, язык, тональность и сущности, предоставляет confidence и позволяет агентам менять значения. Применимый вывод: отдельные поля, пороги уверенности и правка человеком полезнее одного свободного ответа. Intercom Copilot опирается на управляемые источники знаний, показывает источники и даёт редактировать ответ до отправки. Применимый вывод: у админа должны быть видны точные пункты и возможность исправления. Haystack разделяет оценку извлечения релевантных документов и faithfulness ответа — такую же двухэтапную проверку стоит встроить. Эти продукты служат ориентиром сценариев, их заявленные свойства не доказывают качество на данных Grand Mobile.

## 9. Решение о старте

Рекомендуемый порядок: сначала этапы 1–4 и безопасный baseline, затем улучшение качества, затем интерфейс как бонус. Ключевое внешнее решение перед реализацией — подтверждение черновой taxonomy/приоритетов владельцем кейса; если оно задержится, строить с версионированным draft и явно отмечать это в отчёте. Выбор внешнего LLM-провайдера зависит от разрешённых условий обработки данных и измерений на ручном holdout.
