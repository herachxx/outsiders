# Интеграция с Grand Mobile

Реального API игры у нас нет, поэтому интеграция сделана как **односторонний вход**: Grand Mobile присылает обращение, сервис возвращает разбор. Ответы игрокам, санкции и изменения в игре сервис не отправляет — решает администратор.

## Что реализовано

`POST /integration/ticket` принимает запись обращения в том виде, в котором её выдаёт Grand Mobile (поля `ticket_id`, `created_at`, `lang`, `status`, `verdict`, `punishment`, `violation` допустимы, но **игнорируются** и в признаки не попадают). Обязательны `ticket_id`, `kind` и `messages` с хотя бы одним сообщением player.

```powershell
curl -X POST http://127.0.0.1:8000/integration/ticket -H "Content-Type: application/json" -H "X-API-Key: <ключ>" --data-binary "@ticket.json"
```

Ответ: `{"ticket_id": "...", "result": {...}}`. По умолчанию `result` в формате сдачи (`draft_reply.cited` — строки номеров пунктов); `?format=internal` возвращает полные цитаты с хешем.

| Настройка | Назначение |
|---|---|
| `GRAND_API_KEY` | если задан, заголовок `X-API-Key` обязателен (401 иначе); сравнение постоянное по времени |
| `GRAND_RULES_PATH` | правила; без них 503 |
| `GRAND_MODEL_PATH` | обученная модель (необязательно) |
| `GRAND_HISTORY_PATH` | SQLite для повторов и порога 5 обращений за 60 минут; ключом служит `ticket_id` |

Старый `/triage` остался строгим и принимает только поля контракта.

## Как встроить в процесс поддержки

```text
Лаунчер/игра ──новое обращение──► очередь Grand ──POST /integration/ticket──► Copilot
                                                                              │ категория, приоритет, язык,
                                                                              │ цитаты, черновик, needs_human
                                      панель администратора ◄─────────────────┘
                                      (правка → /draft/check → отправка человеком)
```

1. **Вход.** Сервис Grand вызывает эндпоинт при создании обращения и при появлении нового сообщения player. Повтор с тем же `ticket_id` безопасен: результат детерминирован, история ловит конфликт идентичности (409).
2. **Очередь.** Администратор видит очередь по приоритету p0–p3. Значения `priority` и `needs_human` можно записать в карточку обращения на стороне Grand.
3. **Черновик.** Администратор правит текст; проверка `POST /draft/check` не пропускает неподтверждённые цитаты и обещания. Отправка игроку остаётся действием человека в системе Grand.
4. **Обратная связь.** Исправленные категории и приоритеты нужно возвращать для переобучения (разметка администраторов заменяет метки Claude). Для этого в Grand нужно хранить итоговую категорию, назначенную человеком. Сейчас этого канала нет.

## Что потребуется от стороны Grand (чего у нас нет)

- Способ вызова сервиса: webhook или опрос новых обращений; способ записать `priority`/`category` в карточку.
- Подтверждённая taxonomy и приоритеты (сейчас `draft`), решение по «апелляциям» (в нашей разметке это `complaint.admin`).
- Доступ к метке итоговой категории от администраторов для оценки качества в бою.
- Размещение: сервис без внешних вызовов, данные не покидают сервер; хранение — только SQLite с историей (по желанию), срок хранения задаёт Grand.

## Порядок внедрения

1. **Теневой режим.** Сервис получает обращения, результат только пишется в журнал. Сравнение с решениями администраторов даёт настоящую accuracy и macro-F1 на реальных данных.
2. **Подсказки.** Администратор видит категорию, приоритет и черновик, решает сам. Измеряем долю принятых без правки черновиков.
3. **Автоматизация безопасного.** Только после метрик и при отсутствии галлюцинаций: автоприоритизация очереди. Автоответы игрокам не планируются.

## Ограничения

Приоритет p0 и `needs_human` для платежей, доступа к аккаунту и жалоб на администратора защищены правилами, но распознавание kk/uz ограничено, качество подтверждено только на меточных данных Claude (не людей). Метрики — в `PROJECT_MAP.md`.
